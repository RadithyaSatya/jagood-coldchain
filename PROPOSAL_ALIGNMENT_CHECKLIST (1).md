# Checklist Kesesuaian Proposal dengan MVP JaGOOD

Audit repository terhadap `Proposal Jagood.docx` per 20 Agustus 2026. Status kesesuaian: ✅ sesuai, ⚠️ sesuai sebagian/perlu memperjelas batasan, ❌ belum ada atau tidak sesuai. Kelayakan penyesuaian: **BISA** = dapat dikerjakan dari repository, **BERSYARAT** = membutuhkan data/sumber/keputusan tambahan, **TIDAK BISA DENGAN CODING SAJA** = membutuhkan validasi atau kegiatan eksternal, dan **TIDAK PERLU** = implementasi sudah memadai.

| No. | Bagian/klaim dalam proposal | Status | Kondisi project saat ini | Kelayakan penyesuaian dan tindak lanjut |
|---:|---|:---:|---|---|
| 1 | JaGOOD sebagai *decision support* sebelum pengiriman, bukan sistem IoT utama | ✅ | Posisi produk konsisten dengan [README utama](../README.md) dan alur input asal, tujuan, komoditas, moda, serta waktu keberangkatan. | **TIDAK PERLU diubah.** Pertahankan klaim sebagai MVP pendukung keputusan; jangan menyebutnya sistem monitoring real-time. |
| 2 | Cold Chain Risk Prediction memakai XGBoost dengan kelas Low/Medium/High | ✅ | Pipeline, model tersimpan, inferensi, probabilitas kelas, skor risiko, dan *confidence score* tersedia di [feature_pipeline.py](../services/ai/route-planner/app/ml/feature_pipeline.py) dan [ranking_service.py](../services/ai/route-planner/app/services/ranking_service.py). | **TIDAK PERLU untuk fungsi inti.** Cukup tambahkan batasan di proposal bahwa skor valid untuk perbandingan demo, bukan probabilitas kerusakan tervalidasi. Validasi dunia nyata **TIDAK BISA DENGAN CODING SAJA**. |
| 3 | Pembagian data kronologis train/validation/test, *threshold tuning*, dan evaluasi | ✅ | Seluruh alur tersedia di [train_model.py](../services/ai/route-planner/training/train_model.py), [evaluate_model.py](../services/ai/route-planner/training/evaluate_model.py), dan metadata model. | **TIDAK PERLU diubah.** Nyatakan bahwa seluruh split berasal dari dataset sintetis; metrik mengukur kemampuan model mempelajari fungsi label sintetis. |
| 4 | Historical Shipment diperoleh dari data publik, literatur, dan skenario terdokumentasi | ❌ | Tidak ada data pengiriman aktual. `historical_delay_avg_hours` dan `historical_damage_rate` adalah prior deterministik dari asumsi koridor sintetis; lihat [historical_baseline.py](../services/ai/route-planner/app/services/historical_baseline.py). | **TIDAK BISA DENGAN CODING SAJA.** Data aktual membutuhkan mitra/sumber terbuka yang kredibel. Untuk sekarang, ubah proposal menjadi “data sintetis/derived dari asumsi koridor”. Infrastruktur ingestion baru masuk kategori **BISA** setelah dataset tersedia. |
| 5 | Commodity Database dikurasi dari literatur cold-chain dan referensi industri | ❌ | Profil komoditas diklasifikasikan `DEMO`, disusun manual, belum tervalidasi, dan bukan turunan FoodKeeper; lihat [commodity_provenance.json](../services/ai/route-planner/app/data/commodity_provenance.json). | **BERSYARAT — sekitar 2–5 hari.** Bisa diganti dengan referensi resmi, tetapi perlu riset dan validasi sumber per atribut/komoditas. Tanpa itu, proposal harus menyebutnya asumsi internal MVP. |
| 6 | Data BMKG untuk cuaca dan kondisi maritim | ⚠️ | Integrasi BMKG tersedia untuk segmen laut/pelabuhan dengan cache dan fallback berlabel. Rute darat memakai nilai netral terkonfigurasi; suhu kargo pasif memakai Open-Meteo/fallback sintetis. | **TIDAK PERLU untuk MVP.** Sesuaikan narasi proposal agar menyebut BMKG untuk maritim/pelabuhan dan Open-Meteo untuk suhu ambient. Integrasi cuaca darat tambahan **BISA**, tetapi bukan kebutuhan utama. |
| 7 | Data cleaning, missing-value handling, encoding, normalisasi, dan validasi umum | ⚠️ | Encoding kategorikal dan validasi skema tersedia. Fitur numerik XGBoost diteruskan tanpa normalisasi; dataset utama dibangkitkan terstruktur, bukan hasil pembersihan data historis mentah. | **BERSYARAT — sekitar 2–4 hari setelah ada data mentah.** Cleaning dan missing-value handling baru bermakna jika dataset mentah tersedia. Normalisasi tidak wajib untuk XGBoost; lebih tepat menyesuaikan narasi proposal. |
| 8 | Feature Store sebagai sumber fitur terstruktur untuk semua model | ❌ | Tidak ada layanan atau penyimpanan Feature Store. Konsistensi fitur dijaga oleh satu pipeline Python yang dipakai saat training dan inference. | **BISA — sekitar 3–6 hari, tetapi berlebihan untuk MVP.** Opsi ringan adalah menyimpan snapshot fitur di PostgreSQL. Rekomendasi: ubah istilah proposal menjadi “shared feature pipeline”. |
| 9 | Smart Route Recommendation menghasilkan kandidat dan melakukan *risk-based ranking* | ✅ | Kandidat darat/kombinasi dibuat, diperkaya, diprediksi, lalu diurutkan berdasarkan risiko atau kecepatan; lihat [planning_service.py](../services/ai/route-planner/app/services/planning_service.py). | **TIDAK PERLU diubah.** Pertahankan, tetapi sebut sebagai planner MVP—bukan navigasi atau optimizer industri. |
| 10 | Safety check kondisi ekstrem | ✅ | Kondisi ekstrem dapat menurunkan peringkat kandidat dan mengisi `trigger_reason`; sistem tidak memblokir rute secara absolut. | **TIDAK PERLU diubah.** Jelaskan sebagai mekanisme demosi/peringatan, bukan penetapan resmi bahwa pelabuhan atau rute ditutup. |
| 11 | Scenario Simulation Engine membandingkan baseline dan skenario | ✅ | Endpoint `/simulate-scenario` menghitung ulang pipeline untuk perubahan delay, moda, reefer/pasif, dan insulasi, lalu menghasilkan risiko awal, risiko simulasi, delta, faktor berubah, dan rekomendasi. | **TIDAK PERLU untuk fungsi utama.** Pertahankan istilah *deterministic counterfactual*; jangan menyebut Monte Carlo atau model skenario terpisah. |
| 12 | Pengguna dapat mengubah kondisi lingkungan secara langsung dalam simulator | ❌ | Input skenario tidak menyediakan perubahan cuaca, gelombang, atau temperatur secara langsung; kondisi tersebut berasal dari enrichment eksternal/fallback. | **BISA — sekitar 1–2 hari.** Tambahkan override gelombang, angin, cuaca, dan suhu ambient dengan provenance `SCENARIO`, lalu jalankan ulang pipeline analitik. |
| 13 | Route Duration and Delay Estimation menyesuaikan keterlambatan berdasarkan data historis, lingkungan, dan operasional | ⚠️ | Durasi rute dihitung, tetapi `expected_delay_hours` normalnya 0 dan menjadi input tambahan saat simulasi. Prior keterlambatan sintetis dipakai sebagai fitur risiko, bukan model prediksi delay mandiri. | **BISA sebagian — sekitar 1–2 hari.** Baseline delay transparan dan penyesuaian lingkungan dapat dibuat berbasis aturan. Model ML delay yang valid **BERSYARAT** pada tersedianya data planned-vs-actual. |
| 14 | Estimated Product Quality menghasilkan sisa umur simpan, persentase sisa umur simpan, dan quality-retention proxy | ❌ | Sistem menghitung suhu kargo pasif dan *effective consumed hours* secara internal, tetapi respons hanya mengekspos profil suhu dan maksimum kelebihan suhu. Tidak ada keluaran remaining shelf life atau quality-retention proxy. | **BISA — sekitar 0,5–1 hari.** Ekspos hasil Q10 yang sudah dihitung ke API/UI sebagai proxy sisa umur simpan, sertakan provenance dan peringatan bahwa hasil bukan jaminan keamanan pangan. |
| 15 | Recommendation Engine menggabungkan semua modul menjadi satu Final Recommendation | ⚠️ | Orkestrasi route/risk/ranking ada di route-planner, sedangkan scenario dan AI Explain dipanggil terpisah. Tidak ada satu respons backend yang sekaligus memuat rute, skenario, estimasi mutu, dan penjelasan AI. | **BISA — sekitar 2–4 hari.** Tambahkan endpoint agregasi/gateway dan kontrak Final Recommendation. Alternatif lebih ringan: sesuaikan diagram proposal dengan orkestrasi frontend saat ini. |
| 16 | FastAPI Backend sebagai penghubung tunggal seluruh sistem | ⚠️ | Ada dua service FastAPI terpisah: route-planner dan AI Explain. Folder `backend/` tingkat platform masih placeholder; frontend melakukan integrasi antarlayanan. | **BISA — sekitar 3–5 hari.** Folder `backend/` dapat dijadikan platform gateway, tetapi menambah kompleksitas. Untuk MVP, lebih efisien menyebut “FastAPI services” dalam proposal. |
| 17 | LLM hanya sebagai lapisan penjelasan yang *grounded* | ✅ | AI Explain menerima fakta analitik terstruktur, tidak menghitung risiko/rute, dan memiliki fallback deterministik; lihat [AI Explain README](../services/ai/ai-explain/README.md). | **TIDAK PERLU diubah.** Jelaskan bahwa LLM bersifat opsional dan hasil numerik tetap berasal dari analytical engine. |
| 18 | Explainability melalui faktor kontribusi model | ✅ | Faktor per prediksi dihitung dengan SHAP dan ditampilkan sebagai faktor kualitatif. | **TIDAK PERLU diubah.** Tambahkan batasan bahwa kontribusi SHAP berada di *raw-margin space* dan bukan dekomposisi probabilitas yang presisi. |
| 19 | Frontend menampilkan dashboard, alternatif rute, simulasi, dan AI Explain | ✅ | Dashboard Next.js menyediakan perbandingan rute, peta, simulator, profil suhu, faktor risiko, serta panel AI Explain. Chatbot juga tersedia sebagai aplikasi terpisah. | **TIDAK PERLU untuk fitur yang ada.** UI perlu penyesuaian kecil jika output kualitas, delay, atau override lingkungan ditambahkan. |
| 20 | Modularisasi dan deployment dengan Docker Compose | ✅ | PostgreSQL, route-planner, dashboard, AI Explain, dan chatbot didefinisikan di [compose.yaml](../compose.yaml); Ollama dapat berjalan di host atau lewat override. | **TIDAK PERLU diubah.** Jelaskan bahwa PostgreSQL saat ini terutama digunakan untuk cache respons eksternal, bukan Feature Store. |
| 21 | Governance dan klasifikasi asal data | ✅ | Repo telah membedakan `REAL`, `REFERENCE`, `DERIVED`, `SYNTHETIC`, dan `DEMO`, serta mengekspos provenance komoditas. | **TIDAK PERLU diubah.** Salin klasifikasi ini ke bagian dataset proposal supaya klaim data tidak ambigu. |
