# JaGOOD Capability and Claim Matrix

This file describes the repository as implemented today. Product proposals and PRDs may describe future scope; they are not evidence that a capability exists.

## Implemented capabilities

| Capability | Status | What the implementation actually does | Important boundary |
|---|---|---|---|
| Quality-risk classification | Implemented, experimental | A persisted XGBoost pipeline classifies generated route candidates as Low, Medium, or High and produces a weighted risk score. | Training rows and labels are synthetic. Metrics measure recovery of the synthetic label function, not real-world spoilage accuracy. |
| Model training and evaluation | Implemented | Reproducible scripts generate seeded synthetic data, train the preprocessing/model pipeline, and evaluate a held-out synthetic split. | No real labelled shipment outcome dataset is used. |
| Smart Route Planner | Implemented, MVP | Generates land and/or multimodal candidates, enriches them, performs model inference, ranks them by risk or speed, and presents a side-by-side trade-off table. | It is not an industrial routing optimizer or navigation system. ORS failures use haversine-based estimates. |
| Scenario Simulator | Implemented, deterministic | Compares a baseline with changes to delay, mode, cooling equipment, or insulation by re-running the route-risk pipeline. | No Monte Carlo engine, learned scenario model, or uncertainty distribution is implemented. |
| FastAPI platform gateway | Implemented | Provides the single public API used by the planner dashboard and chatbot, proxies internal services, exposes readiness, and orchestrates Final Recommendation. | Route Planner and AI Explain remain separate internal services; the gateway is an integration layer, not a monolith. |
| Maritime risk input | Implemented with explicit fallback | Uses BMKG maritime/port forecasts when reachable and derives a port-risk proxy from wave category. Expected network/malformed-response failures use neutral fallback values labelled in `environmental_data_quality`. | Port status is not official operational status and `searoute-py` geometry is not navigation-grade. Fallback values reduce demo failure, not uncertainty. |
| Land weather and adaptive delay | Implemented, MVP | Uses Open-Meteo weather for land routes, applies a transparent bootstrap weather-delay adjustment, and can blend checkpoint-derived observations after sufficient samples accumulate. | This is not a separately trained or validated delay-regression model; learned checkpoint attribution currently applies to land routes. |
| Passive cargo-temperature and quality proxy | Implemented, assumption-based | Simulates passive cargo temperature with an exponential heat-transfer/Q10 approach and exposes remaining shelf-life hours, percentage, and a coarse quality status. | Reefer shipments assume ideal cargo temperature. There are no physical sensors or calibration data; outputs are proxies, not food-safety guarantees. |
| Shipment history and checkpoints | Implemented, pilot infrastructure | Persists route predictions, selected routes, manual browser-geolocation checkpoints, and reported actual outcomes in PostgreSQL. Corridor/weather statistics can gradually blend real reports into bootstrap priors. | The repository does not ship with sufficient real outcomes, continuous GPS/IoT telemetry, authentication, or fleet monitoring. |
| SHAP explanation factors | Implemented | Computes per-route SHAP contributions and renders the strongest qualitative factors. | Contributions are combined in raw-margin space and are not an exact probability decomposition. |
| AI Explain | Implemented, optional LLM | Sends structured analytical facts to an OpenAI-compatible LLM for natural-language explanation. | The LLM does not calculate routes or risk. A deterministic fact-only fallback is used when inference is unavailable. |
| Offline golden demo | Implemented | Tests route fallback, risk/SHAP inference, scenario comparison, and AI Explain fallback without ORS or an LLM. | It demonstrates technical integration, not external-data availability or real-world accuracy. |

## Data truth table

| Data | Classification | Current use |
|---|---|---|
| Commodity profiles | Mixed `REFERENCE` and `DEMO` | Temperature and shelf-life fields cite FDA, USDA/FSIS, UC Davis, and IDFA sources. Delay tolerance and temperature sensitivity remain internal MVP assumptions. Metadata is exposed at `GET /commodities/provenance`. |
| Model training shipments and risk labels | `SYNTHETIC` | Generated by seeded rules plus noise for training and evaluation. |
| Historical delay/damage features | Initially `DERIVED`, adaptable with `REAL` outcomes | Deterministic corridor priors are used initially and can blend reported actual outcomes after sufficient samples accumulate. No real outcome dataset is bundled. |
| OpenRouteService route response | External runtime data | Used for land geometry/duration when available; otherwise marked `data_quality: estimated`. |
| BMKG maritime forecast | External runtime data with labelled fallback | Used for sea/port enrichment when reachable. Responses are cached; expected failures use neutral defaults labelled `fallback`/`partial`. |
| Open-Meteo weather and temperature | External runtime data with labelled fallback | Used for land-route weather and passive-cargo ambient temperature; configured/synthetic fallbacks preserve availability. |
| Shipment outcomes/checkpoints | `REAL` when reported | Stored through shipment outcome and checkpoint endpoints; absent until users or pilot operators submit actual journeys. |

## Not implemented

- continuous GPS or IoT ingestion and real-time fleet monitoring
- a separately trained delay-prediction model
- scientifically validated or guaranteed product-quality/shelf-life estimation
- economic-loss estimation
- Monte Carlo simulation or quantified uncertainty intervals
- production-grade feature store with registry/versioned online serving
- reinforcement-learning route optimization
- authentication, notifications, and production authorization controls

These items may appear in proposal or roadmap material only as future scope. They must not be presented as working features during the MVP demo.
